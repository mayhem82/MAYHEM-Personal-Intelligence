BEFORE YOU START
- Accounts: the owner needs GitHub, an AI provider account and a server host for ClarityPath's required AI. The AI-assisted installation route also needs a coding assistant with GitHub access. Check account access before committing to a plan.
- Two AI roles: a coding assistant helps install and maintain the system. The AI service inside ClarityPath answers approved requests from selected case material. Connecting the coding assistant to GitHub does not create or activate the site's AI service.
- Costs: the coding assistant, server hosting and provider API may have separate charges or usage limits. Check the current plans and agree a spending limit before enabling billed services. A request-count cap is not a guaranteed currency limit.
- Ownership: use the recipient's own public application repository and a different private case-data repository. The public repository contains the website's code. Preserve Julian Minko's creator attribution. An alias does not guarantee anonymity.
- Privacy: case records and originals must be encrypted before private repository upload. The selected payload goes to the configured AI provider only after its separate review/approval. Never put case data, tokens or passphrases in the public repository or replication pack.
- Permissions and secrets: give the coding assistant only the repositories needed for installation. It does not need private case content to copy the public application. Enter credentials in the relevant account, host or ClarityPath password field, not ordinary AI chat. Review requested access and any publication before approving it.
- Recovery: keep the GitHub recovery methods, encryption passphrase and an independent encrypted backup somewhere you control. ClarityPath cannot reset a lost encryption passphrase. An unlocked or downloaded readable ZIP needs private storage too.
- Devices: both guides below are readable on a phone. Some initial repository file uploads and cloud-environment creation use web/desktop screens; a computer may be easier for folder uploads. Codex mobile can use an already published cloud environment. No account action is required simply to read this guide.
- Current limits: inspect release-status.json before real-case use. Source code and a configured connection are not proof of working live AI. The included service has process-local request limits; automatic GitHub App sign-in, recovery-key rotation and full investigation orchestration are not complete. No independent security or legal-compliance audit is claimed.
- Completion: confirm the new owner's actual deployed URL, a verified encrypted private save/reopen, a real approved synthetic AI response, recovery and selected handoff. Any missing connection or implementation item remains explicitly incomplete.
Reference: Current implementation and verification status | ./build.html#release-status

FIRST, SET UP YOUR GITHUB ACCOUNT
1) Open GitHub signup, create or sign in to the owner's personal account, and complete email verification. The owner keeps control of the login and recovery email.
2) Set up two-factor authentication and keep the recovery information privately. Choose the public username/alias and review which profile and commit email details will be visible.
3) Create the owner's public application repository, for example claritypath. Add a README so it has an initial branch. Record the actual owner/repository and default branch.
4) Create a different repository for the owner's case data. Select Private and add a README. Keep GitHub Pages off for this private case repository.
5) Choose the manual route below, or connect a coding AI using the next section. Creating these repositories does not yet install the application or connect its runtime AI.
Reference: Create a GitHub account | https://docs.github.com/en/account-and-profile/how-tos/account-management/creating-an-account-on-github
Reference: Open GitHub signup | https://github.com/signup

CONNECT A CODING AI TO YOUR GITHUB, IF USING THE AI ROUTE
1) Choose a coding assistant that can edit a repository, run checks and propose or publish changes. Check that your account has the required access. A code-search connection alone does not perform the installation.
2) One supported example is Codex Cloud. Sign in to ChatGPT. On the web or desktop, choose Work in, then Cloud, open Select environment and choose Create environment.
3) Select the new owner's public application repository. Connect GitHub if prompted, sign in as that owner and review the requested permissions. Where repository selection is offered, limit access to the selected application repository. Do not grant access to private case content merely to copy public code.
4) Select Get started, review the prepared environment and any missing access, save it and select Publish. Wait for Environment published. On mobile, select the published environment in Codex.
5) Start a new task in that environment. Give it the ClarityPath source repository or complete Build pack, together with Copy AI setup instructions below. Check that the task names the owner's new repository as its destination before accepting a push or publication.
6) Review the actual changes and test results. The owner still controls account verification, private credential entry and any charge approvals. Then follow the same completion checks as the manual route.

CLARITYPATH — COMPLETE INSTALLATION FOR A NEW OWNER

TASK FOR THE AI RECEIVING THIS REPOSITORY OR BUILD PACK
Complete the installation of the recipient's own personal intelligence system. Reproduce the application, set up the recipient's own repositories and required services, connect them, verify the working system and deliver its operating and recovery instructions. Carry the authorised setup through to a concrete result. The following steps are part of the installation task.

1. ESTABLISH THE DESTINATION
Use the new owner's GitHub account under their chosen name or alias. Establish their chosen public application repository and a different private case-data repository. Identify who controls the accounts and recovery methods, which host/provider the setup session authorises, and any authorised spending limit. Use details already available in the session or connected account before asking for them. The owner completes account verification and private credential entry. Work that does not depend on those steps can continue.

2. CREATE THE OWNER'S PUBLIC APPLICATION REPOSITORY
Create or use the authorised new public repository in that owner's account. Copy the current clean public source or reconstruct the exact files from the complete Build pack, including the binary assets, dotfiles, tests and workflow. Preserve the creator attribution and source notices. Point the new checkout's origin at the owner's new repository and verify the destination before any push. Keep the source author's repository as a reference; its account, repositories, credentials and live services are not the new installation's destinations.
Use the actual default branch in the included Pages workflow. Configure GitHub Pages to deploy through that workflow, push the verified public source and publish only the generated site/ directory. Record the new owner's actual site URL. Check that workspace, Build, recipient unlock page, icons, install scope and navigation resolve under that repository's URL.

3. SET UP THE SEPARATE PRIVATE CASE STORE
Create or use the authorised private repository owned by the actual case-data owner. Initialise it with a harmless README so the application can access its default branch. Verify its private visibility and identity before connecting. The public application repository and private case repository must be distinct.
Configure the implemented connection using an expiring fine-grained token restricted to the selected private repository with Contents read/write and necessary metadata read. The token stays in memory. Set up the owner's encryption passphrase privately, initialise the encrypted store in ClarityPath and perform the first verified save. Set up encrypted device saving if the owner wants it, and give them an independently stored encrypted backup and recovery instructions. Keep the passphrase separately.
Test with clearly labelled synthetic records and files: save, lock, reopen, unlock and confirm the exact text and original file bytes. Confirm that another case remains isolated and a stale remote revision is not silently overwritten. Record live verification separately from fixture-based tests.

4. DEPLOY AND CONNECT THE REQUIRED AI SERVICE
AI is a required installation component. Deploy service/server.mjs to the owner-controlled HTTPS server authorised in the setup session, using service/README.txt and service/Dockerfile where applicable. Complete the hosting and provider setup rather than leaving a list of services for the owner to research. Keep the public application on its new GitHub Pages site.
Configure the owner-controlled provider key, available model, service access key, allowed origins and request limit through the host's private settings. ALLOWED_ORIGINS must contain the new site's exact origin, derived from its actual URL, without its repository path. Set the host's bind/port and health-check settings. Do not reuse the source author's origin, key, endpoint or account. Keep one service process unless a durable shared quota/idempotency mechanism has been implemented and checked.
Verify /healthz and authenticated capabilities, then connect the real HTTPS endpoint in the new workspace. A configuration check does not verify a provider response. With the owner's applicable transmission/spending authorisation, select only a synthetic record, review and approve the actual payload, obtain a real cited provider draft and confirm it is saved separately. Check that unselected material, attachments and private build specifications are absent from the request. Real case material needs its own explicit selection and approval.
If authentication, host access, a provider credential or charge approval is missing, finish the independent work and name the exact remaining owner-controlled step. Keep AI setup marked incomplete until a real authorised provider request succeeds. Do not substitute canned output or claim that service source code alone is live AI.

5. VERIFY THE OWNER'S PERSONAL INTELLIGENCE WORKSPACE
Run node scripts/package-release.mjs and npm test. Run the browser and PWA checks with the declared Playwright dependency and supported browser. Test the actual deployed installation as well as the local source: NSW situation selection, a new private case, original account and attachment, chronology and links, separate review/source handling, the ordered engine workflow, summaries and selected handoff.
Test a protected selected handoff in a clean recipient browser without the owner's private-workspace connection. Confirm the exact recovered ZIP/original bytes and excluded-record boundary. Check mobile layout, installable scope, public-only offline caching, encrypted reload and lock. Report a physical-device test only if it occurred. Retain test records as clearly identified private fixtures unless the owner authorises their removal; ordinary use must not start with fictitious personal case material presented as real.

6. FINISH THE NEW OWNER'S REPLICATION AND RECOVERY PACK
Regenerate Build, build-pack.txt, source-manifest.json and release-status.json from the new installation's actual public source. Include these setup instructions so that the next authorised owner can repeat the process for their own repositories and system. Publish that matching pack alongside the tested site. Keep credentials, private repository details and case data out of the public pack.
Give the owner their public site and repository links, how to reopen private work, renew the restricted connection, keep backups, recover with the passphrase, use AI payload approval and prepare a selected handoff. Keep any private setup report in an ignored private location such as .private-build/; public status records may report verification outcomes without private identifiers or secrets.
List the actual checks performed and any unresolved implementation or configuration items. Completion means the owner's deployed system and real connections work as verified. An unavailable owner-controlled step remains an explicit blocker, not a completed installation.
