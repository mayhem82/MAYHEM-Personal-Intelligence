BEFORE YOU START
- Complete system installation: finish the owner’s public site, backend service, required artificial intelligence connection, the separate private case repository already created for this installation, and verified recovery. Adding a phone icon opens the published site; account and service configuration remain part of the full setup. Mark installation complete only after the connection and recovery checks succeed.
- Guided installation: choose Set up my system on Home, or Installation in the workspace. Select Manual setup or With a coding assistant, read the concerns, then follow the six stages. Next names the earliest unfinished action. Verified this session means an application check succeeded; Owner confirmed is your statement; Prepared for download does not prove that you saved or independently opened the file. This checklist lasts only while the workspace is open. Locking or refreshing clears it; returning Home retains it. Account creation and service deployment use the directions and your own accounts.
- Accounts: the owner needs GitHub, an artificial intelligence provider account and a server host for ClarityPath's required artificial intelligence. The artificial intelligence-assisted installation route also needs a coding assistant with GitHub access. Check account access before committing to a plan.
- Two artificial intelligence roles: a coding assistant helps install and maintain the system. The artificial intelligence service inside ClarityPath answers approved requests from selected case material. Connecting the coding assistant to GitHub does not create or activate the site's artificial intelligence service.
- Costs: the coding assistant, server hosting and provider application programming interface may have separate charges or usage limits. Check the current plans and agree a spending limit before enabling billed services. A request-count cap is not a guaranteed currency limit.
- Ownership: use the recipient's own public application repository and a different private case-data repository. The public repository contains the website's code. Preserve Julian Minko's creator attribution. An alias does not guarantee anonymity.
- Privacy: case records and originals must be encrypted before private repository upload. The selected payload goes to the configured artificial intelligence service only after its separate review/approval. The artificial intelligence host and provider process that selected text in readable form; review their privacy, retention and data-handling terms before using real case material. Never put case data, tokens or passphrases in the public repository or replication pack.
- Permissions and secrets: give the coding assistant only the repositories needed for installation. It does not need private case content to copy the public application. Enter credentials in the relevant account, host or ClarityPath password field, not ordinary artificial intelligence chat. Review requested access and any publication before approving it.
- Recovery: keep the GitHub recovery methods, encryption passphrase and an independent encrypted backup somewhere you control. ClarityPath cannot reset a lost encryption passphrase. An unlocked or downloaded readable ZIP needs private storage too.
- Devices: both guides below are readable on a phone. Some initial repository file uploads and cloud-environment creation use web/desktop screens; a computer may be easier for folder uploads. Codex mobile can use an already published cloud environment. No account action is required simply to read this guide.
- Current limits: inspect release-status.json before real-case use. Source code and a configured connection are not proof of working live artificial intelligence. The included service has process-local request limits; automatic GitHub App sign-in, recovery-key rotation and full investigation orchestration are not complete. No independent security or legal-compliance audit is claimed.
- Completion: confirm the new owner's actual deployed URL, a verified encrypted private save/reopen, a real approved synthetic artificial intelligence response, recovery and selected handoff. Any missing connection or implementation item remains explicitly incomplete.
Reference: Current implementation and verification status | ./build.html#release-status

FIRST, SET UP YOUR GITHUB ACCOUNT
1) Open GitHub signup, create or sign in to the owner's personal account, and complete email verification. The owner keeps control of the login and recovery email.
2) Set up two-factor authentication and keep the recovery information privately. Choose the public username/alias and review which profile and commit email details will be visible.
3) Create the owner's public application repository, for example claritypath. Add a README so it has an initial branch. Record the actual owner/repository and default branch.
4) Create a different repository for the owner's case data. Select Private and add a README. Keep GitHub Pages off for this private case repository.
5) Choose the manual route below, or connect a coding artificial intelligence using the next section. Creating these repositories does not yet install the application or connect its runtime artificial intelligence.

CLARITYPATH — MANUAL INSTALLATION STEPS
© 2026 Julian Minko · Architect of MAYHEM · ClarityPath

1. COPY THE PUBLIC APPLICATION
1) Complete Start here above. Open the source application repository, choose Code, then Download ZIP. Extract the current source snapshot. The download contains application code, not anyone's private workspace.
2) Open the new owner's public application repository. Choose Add file, then Upload files. Upload the extracted project's contents into the repository root, including its folders, .github workflow folder, dotfiles, assets and setup instructions. Do not upload an extra enclosing folder or a private backup.
3) Commit the upload. If you use Git or GitHub Desktop instead, copy the source snapshot into the new repository's checkout, confirm its origin is the new owner's repository, then commit and push there.
4) Confirm that index.html, workspace.html, package.json and .github/workflows/deploy-pages.yml are at the expected paths in the new repository. Confirm app/startup.mjs, app/home-view.mjs, app/installation.mjs and app/installation-state.mjs are included. The package command regenerates the Home view from the public index.html; keep private records out of it. Keep the copyright/source notices.
Check: the address bar and repository owner show the recipient's new public repository.
Reference: Source application repository | https://github.com/mayhem82/MAYHEM-Personal-Intelligence
Reference: Upload repository files | https://docs.github.com/en/repositories/working-with-files/managing-files/adding-a-file-to-a-repository

2. PUBLISH THE OWNER'S SITE
1) In the new public repository, open Settings, then Pages. Under Build and deployment, set Source to GitHub Actions. The repository already supplies the Publish ClarityPath workflow.
2) Check that the workflow's push branch matches the repository's actual default branch. If it differs from main, edit the branch name in .github/workflows/deploy-pages.yml and commit the change.
3) Open Actions, select Publish ClarityPath and run it for that branch if a successful deployment has not already occurred. Wait for its checks and deployment to succeed.
4) Open the published URL shown in Pages or the deployment. Check Home, Workspace, Psychological First Aid, Build, setup instructions, the operating guide and the protected-handoff unlock page. Record your actual site URL; do not reuse the source author's site address. On the owner's Home choose Set up my system, select Manual setup and use the six-stage Installation screen alongside these directions.
Check: Home opens first, Workspace contains the public situation catalogue, and Build contains the matching full replication pack. Continue the private-storage, service and verification steps to complete installation.
Reference: Configure GitHub Pages publishing | https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site

3. CONNECT AND TEST PRIVATE STORAGE
1) Open the separate private case repository and confirm it contains its initial README and is marked Private.
2) In GitHub account settings, open Developer settings, Personal access tokens, then Fine-grained tokens. Create an expiring token for the owner's account, selecting only the private case repository. Give it Contents read/write and the necessary metadata read access. Keep the token privately.
3) In the owner's ClarityPath site, open Storage & connections, then Connect a private GitHub repository. Enter the private owner/repository and token in Restricted access token. Choose Connect private repository.
4) Enter a new Repository encryption passphrase of at least 12 characters. Under Action choose Initialise a new encrypted workspace, then Continue. Keep this passphrase separately.
5) Create a clearly labelled synthetic test situation and record, attach a harmless test file, then choose Save privately. Wait for Private save verified. In Installation choose Read saved workspace and unlock with the same passphrase. Compare the reopened record text and downloaded original with your test file, then confirm that comparison. The application validates the encrypted workspace; you check its contents. Test Lock / close and reconnection separately as well; locking starts a new checklist.
6) Under Download an encrypted backup, choose a backup passphrase and save the backup independently. In Installation, select that encrypted file, enter its passphrase and choose Verify backup without replacing work. The application decrypts, validates and compares it locally; it leaves current work in place and clears the password field. Confirm the independent backup location separately. If you want encrypted saving on this device, use Keep an encrypted copy on this device. Reconnection after a lock/reload uses the same private repository; do not initialise over an existing vault.
7) After connecting and unlocking the private repository, choose Remember private connection on this device. Protect it with the device passphrase when prompted. Lock or reopen the app, unlock saved work, and verify that the same private repository reconnects. Repeat Save privately and check its verification. Keep the independent backup and passphrases separately. If another device changed the remote work, review the additive merge before saving; cancelling the review must keep saving blocked.
Check: private save and reopen preserve the exact test account and original bytes. A local device copy is a separate save mechanism.
Reference: GitHub token setup | https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens

4. DEPLOY AND CONNECT THE SITE'S ARTIFICIAL INTELLIGENCE
1) Create or sign in to the owner's artificial intelligence provider and chosen HTTPS hosting accounts. The supplied server uses the OpenAI Responses application programming interface. In the provider project, create an application service account/key with the needed model access and set the account's cost controls. Choose an available model supporting the required Responses and web-search capabilities.
2) A concrete hosting route is Render: open the dashboard, choose New, then Web Service and connect the owner's public application repository. Select the intended branch, a Node runtime of version 22 or later, build command node --version and start command node service/server.mjs. Review the host's plan and charges before creating the service.
3) In the host's private environment settings enter the following values. Use the host-provided PORT. Configure the health-check path as /healthz, and keep one service process while quota/idempotency storage is process-local.
ENV OPENAI_API_KEY = The provider project service-account key, stored only on the server.
ENV OPENAI_MODEL = The exact supported model identifier available to that account.
ENV SERVICE_ACCESS_KEY = A separately generated random service password of at least 24 characters, kept privately.
ENV ALLOWED_ORIGINS = The owner's actual site origin, such as https://YOUR-USERNAME.github.io, without /repository-name/.
ENV MAX_REQUESTS_PER_DAY = 30, or the owner's chosen request cap. This is not a currency guarantee.
ENV HOST = 0.0.0.0
4) Deploy and wait for the service to report ready. Opening its /healthz URL should return ready. This checks settings, not the provider. If a free host is sleeping, let this URL wake it before connecting from ClarityPath.
5) In ClarityPath, open Storage & connections, then Connect required artificial intelligence and research service. Enter the final HTTPS Service address and the SERVICE_ACCESS_KEY in Service access key. Choose Connect service. The provider application programming interface key does not go in this browser field.
6) In Summaries & handoff select only your synthetic test record, open artificial intelligence narrative assistance, enter a summary question and choose Preview artificial intelligence request. Check the destination, question and selected material, then approve the request. Verify that the returned draft cites the selected record and remains separate from the original.
Check: a real approved provider draft has returned. A ready health check or connected coding assistant alone does not establish working site artificial intelligence.
Reference: Official OpenAI key guidance | https://developers.openai.com/api/docs/guides/api-keys
Reference: Render web services | https://render.com/docs/web-services
Reference: Render free-host limitations | https://render.com/docs/free

5. TEST THE PERSONAL INTELLIGENCE WORKFLOW
1) Browse a New South Wales situation, create a private case and record a synthetic firsthand account with its actual date precision, source, certainty and dispute fields. Add a file and a related record. Confirm switching cases keeps them separate.
2) Add a separate review and a source passage with its actual URL, provision/version and case relevance. Use the operating guide for qualification, snapshots, authorised analysis and the ordered Solicitors Advocate Engine workflow. Do not invent facts or authority to make a test pass.
3) Create a structured summary, then Preview protected handoff for an explicit selection. Review its scope and confirm a separate handoff passphrase. Open the protected file at the owner's handoff.html page in a clean browser, unlock it, download/extract the readable ZIP and compare its selected records and original files.
4) In Storage & connections choose Verify records and attachments. Test encrypted reload and lock, backup recovery in a separate empty test workspace, phone layout and installation. Keep clearly labelled test material separate from real case work.
5) Install the owner’s app from Home when testing on a phone. Open the icon and check that Home appears. Enter Workspace, keep a clearly labelled test record and some unfinished form text, leave the app running, switch to another app and tap the ClarityPath icon again. Expect Home; choose Open my workspace and confirm the record and unfinished text remain. Selecting a file and returning from its picker should keep the current form. Returning Home is not a save; verify private saving or an encrypted backup before fully closing the app. Record a real phone result only when you have performed it.
6) If testing an older installed copy, save any existing work and choose Home once to load the updated public application before retesting its launcher. Keep the same installation identity and private device data. The automated launch check below covers the older address and the return path without native browser launch support.
7) If running the source locally with Node.js and the declared development dependency, run the package and test commands. The published workflow runs package/core checks, while manual use of the actual site verifies the live connections and recipient experience.

Check: record any failed or unperformed checks. A physical-phone check and a browser emulation check are different results.

6. KEEP YOUR OWN SYSTEM READY TO USE
1) After any source changes, regenerate the public site and matching Build pack, commit the authorised public source to the owner's repository and let its workflow publish. Keep case records and credentials in their private locations.
2) Keep the owner's public site/repository links, private connection details, token renewal date, encryption passphrases, service URL/access key and provider/host account recovery information privately as appropriate. Save an independent encrypted backup.
3) Confirm the copied Build pack contains both manual and artificial intelligence setup instructions for a future owner. Keep the creator attribution and public/private boundary intact.
4) Review Finish and review in Installation. New records or drafts change the workspace revision and require a current private save, backup check and handoff. A failed replacement connection or check clears the corresponding success. A prepared download is not a verified saved copy. Refreshing or locking clears this session checklist; it is not a durable setup report.
5) Before treating installation as complete, confirm the actual private save/reopen, real approved synthetic artificial intelligence response, recovery and recipient handoff. Record unresolved implementation/configuration items from release-status.json. Creating the system does not send a complaint, contact a solicitor or share the private repository.
Check: the owner controls the accounts, can reopen the work and knows how to keep it and choose what to share.
